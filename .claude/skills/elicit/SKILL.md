# 需求訪談（/elicit）

目標：用**最少的使用者心力**，產出一份使用者讀完會說「對，就是這個」的 `.bridge/SPEC.md`。
SPEC 的核心是**可測試的驗收條件（AC）**，因為之後 AC 會直接變成驗收測試。

## 原則

- **選擇題優於申論題**：用 `AskUserQuestion` 提問，每題 2–4 個選項，把你推薦的放第一個並標「（推薦）」。只有真的無法列舉時才問開放題。
- **每輪最多 4 題，最多 3 輪**。超過代表你在問不重要的事；改成寫進「假設」讓使用者在檢查點一次確認。
- **只問「低信心 × 高影響」的事**。你有把握的、或錯了也容易改的，直接當假設。
- **展示優於詢問**：涉及畫面、流程、輸出格式時，做原型讓使用者挑，不要用文字描述問。
- **不重複問**：先讀 `.bridge/USER_PROFILE.md`，已知的偏好直接套用。
- 全程用使用者的語言（繁體中文）。

## 流程

### 第 0 步：載入脈絡

1. 讀 `.bridge/USER_PROFILE.md`、`.bridge/SPEC.md`（可能是空白範本、被退回的草稿，或有變更請求）、`.bridge/FEEDBACK.md`、`.bridge/CHANGE_REQUESTS.md`。
2. 如果 SPEC 是被退回或要變更：只針對回饋的部分修改，不要重新訪談全部。直接跳到第 4 步。
3. 判斷是**新專案**還是**既有專案**：專案資料夾裡除了 bridge 自己的檔案（`.bridge/`、`.agent/`、`.claude/`、`AGENTS.md`、`CLAUDE.md`、`GEMINI.md`）之外，還有其他檔案，就是既有專案。
   - 新專案：使用者還沒描述想法的話，請他用一兩句話描述。
   - 既有專案：先做下面的「既有專案模式」，再進第 1 步。

### 既有專案模式（只在既有專案時做）

目標：先搞懂「現在是什麼」，讓訪談只聚焦在「接下來要改什麼」，不要問使用者自己早就做完的事。

1. **盤點現況**（不要問使用者，自己讀）：
   - 程式碼、README、設定檔：這是什麼、怎麼執行、用了哪些技術
   - 檔案很多時（例如大量 PDF、Word 資料），只看檔名與結構，抽樣讀幾份，不要全部讀完
   - 既有的 `AGENTS.md`／`CLAUDE.md` 中，原作者留下的規則
2. 寫進 SPEC 的「## 現況」區塊（範本沒有這個區塊的話，加在「一句話目標」之前）：
   - 3–6 行描述：它是什麼、目前能做什麼、怎麼執行
   - 「必須保留的既有行為」清單：哪些功能、檔案格式、路徑是其他東西依賴的，改了會壞
3. 用一輪 `AskUserQuestion` 確認：
   - 你對現況的理解對不對（列出 2–3 個你最不確定的點讓使用者選）
   - 這次想做哪一種：修 bug／加功能／重構整理／改善外觀／其他
4. 之後的步驟照常進行，但要注意：
   - 第 1 步：專案類型、使用者是誰這些能從現況推論出來的，不要再問
   - 第 4 步：除了新需求的 AC，「必須保留的既有行為」也要各寫成一條 `[必要]` AC（回歸驗收），例如「AC-9 [必要]：Given 既有的 tasks/ 資料夾，When 執行排程腳本，Then 產生的每日筆記格式與改版前相同」
   - 「非目標」要明確寫出「不重寫 ○○」，防止 agent 把整個專案翻掉重做

### 第 1 步：分類與範圍（第 1 輪提問）

把 SPEC frontmatter 的 `status` 設成 `drafting`。

用一輪 `AskUserQuestion` 釐清以下這些（能推論出來的就不問）：

- **專案類型**：web / script / app，然後讀對應的參考檔：
  - web → `references/web.md`
  - script（CLI、自動化、資料處理）→ `references/script.md`
  - app（桌面、手機）→ `references/app.md`
- **使用者是誰**：只有自己 / 少數人 / 公開
- **成功的樣子**：例如「每天省 10 分鐘」、「能 demo 給老師看」、「上線給 100 人用」
- **時程與規模**：週末小作品 / 數週 / 長期維護

把類型寫進 `.bridge/config.toml` 的 `[project] type`。

### 第 2 步：假設表（第 2 輪提問）

根據目前資訊，加上參考檔的「常見盲點」，**先自己列出所有假設**，每條標上：

| # | 假設 | 信心 | 影響 |
|---|---|---|---|
| A1 | 資料存在本機 SQLite 即可 | 高 | 中 |
| A2 | 需要登入 | **低** | **高** |

只針對「信心低 × 影響高」的假設提問，其餘保留在表中。

### 第 3 步：原型（只在需要時）

如果 SPEC 有「畫面配置／互動流程／輸出格式」沒有定案，而且這件事影響大，就做原型：

- **自己做**：在 `.bridge/prototypes/A|B|C/` 各放一個單檔 HTML（或 CLI 的假輸出 `demo.txt`），方向要明顯不同。
- **或交給 Antigravity**：請使用者在 Antigravity 執行 `/bridge-prototype`，它會截圖，視覺比較更直觀。

用 `AskUserQuestion` 讓使用者選，可以複選「A 的版面 + B 的配色」。

### 第 4 步：寫 SPEC

照 `.bridge/SPEC.md` 範本的結構填寫。重點：

- **AC 用 Given / When / Then 寫，每條都要能被一個人或一個瀏覽器 agent 實際驗證**。
  - ❌「介面要好用」
  - ✅「AC-3：Given 未登入，When 點擊『儲存』，Then 彈出登入視窗，且輸入內容不遺失」
- 每條 AC 標優先級：`[必要]` 或 `[加分]`。
- **非目標**至少列 3 條，防止範圍膨脹。
- 「未決問題」區塊必須清空；還不確定的事，轉成假設並標出來。
- frontmatter 的 `questions_asked` 填這次訪談實際問了幾題（含原型選擇）。

### 第 5 步：事前驗屍（最後一題）

問一題開放題：

> 「想像做完之後你看了很失望，最可能是因為什麼？」

根據回答，補 AC 或非目標。這題常會挖出沒說出口的真正需求。

### 第 6 步：交給檢查點

1. 把 SPEC frontmatter 的 `status` 設成 `ready`。
2. 在對話中給使用者一份**很短的摘要**（10 行以內）：一句話目標、必要 AC 數量、最關鍵的 3 個假設、非目標。
3. 告訴使用者：
   - 檢查沒問題 → 執行 `python3 .bridge/bridge.py run`（會進入人類核准檢查點），然後 `python3 .bridge/bridge.py approve`
   - 要修改 → 直接告訴你，或執行 `python3 .bridge/bridge.py reject -m "原因"`
4. 更新 `.bridge/USER_PROFILE.md`：把這次訪談學到的**可重複使用**的偏好記下來（技術棧、風格、在乎的點），只寫使用者明確表達過的，不寫你的猜測。

## 不要做的事

- 不要在 SPEC 寫實作細節（用哪個函式、檔案怎麼切），那是 PLAN 階段的事。只有使用者明確指定的技術（例如「一定要用 Python」）才寫進「限制」。
- 不要自己核准 SPEC，也不要修改 `.bridge/state.json`。
