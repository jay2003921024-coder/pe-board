## 對 r1 問題的驗證

r1 指出的根因：`load()` 原本在拿到 `getRedirectResult` 後立刻同步 `emit(resumeCbs, intent)`，但 `user`／`userKnown` 要等 `onAuthStateChanged` 的非同步初次回呼才會設好，導致 `onResume` 訂閱者（`sharearea.js` 的 `startPublish`）看到的 `currentUser()` 還是 `null`，誤判成未登入又跳出一次登入提示。

修法（`js/store/firebase.js:57-71`）：
- `getRedirectResult` 成功時只把待辦動作存進區域變數 `resumeIntent`（不再提前 emit）。
- 真正的 `emit(resumeCbs, resumeIntent)` 移到 `fb.au.onAuthStateChanged(...)` 的**初次回呼內部**、且在 `user = toUser(u); userKnown = true; emit(userCbs, user);` **之後**才執行（第 64-70 行）。這保證 `onResume` 的訂閱者在收到通知的那一刻，`currentUser()` 已經是轉址登入回來的使用者。
- 另外加了一行 `if (resumeCbs.size) pendingResume = null;`，避免已經即時交付過一次之後，晚註冊的訂閱者（`onResume` 的 `subscribe(..., now)` 邏輯）又收到同一個待辦動作一次，維持「只交出一次」的語意。

對照 `js/ui/sharearea.js:166` 的 `onResume(intent => { openSharedTab(); startPublish(intent); });`，以及 `startPublish`（`sharearea.js:152-161`）裡 `currentUser()` 的判斷，這個修法确實讓 redirect 回來後直接走「已登入」分支，開發布確認對話框，不會再誤判成未登入。

新增的測試 `tests/unit/firebase.test.js:122-133`（`onResume 觸發時 currentUser() 已經是轉址登入回來的使用者`）直接重現 r1 給的重現步驟（`RESUME_KEY` 先存好待辦、`getRedirectResult` 回傳已登入使用者），斷言 `onResume` 回呼內 `currentUser()` 非 null 且 `uid` 正確；修法前會失敗（沿用 r1 的邏輯分析可驗證），修法後通過。另外兩筆既有的 `onResume` 測試（`popup 被擋...`、`onResume 晚註冊...`）因應事件改成非同步交付，補上了 `await new Promise(r => setTimeout(r, 5))` 等待 `onAuthStateChanged` 初次回呼跑完才斷言，且「晚註冊」測試把第二個訂閱者改成等待之後才訂閱——這樣才能正確驗證「只交出一次」在新時序下仍然成立，測試邏輯正確、沒有為了讓測試過而弱化斷言。

這個修法範圍限定在 `firebase.js` 的這一段時序 bug，沒有動到 007 交付的其他邏輯（Firestore 規則、存取層其他函式），符合任務檔「交接筆記」裡的說明，也符合「只處理自己任務」的協作規則（007 與 008 同為 claude，不是跨 agent 修改）。
