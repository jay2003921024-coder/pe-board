## 發現的問題

### AC-20（redirect 登入回來後不應再要求登入一次）不滿足：`onResume` 觸發時 `currentUser()` 還是 `null`，導致又跳出「需要登入」提示

- 對應 AC：AC-20（「登入完成後回到原畫面，正在編輯的教案內容不遺失」）；任務檔「實作提示」明確要求 redirect 路徑是「`initFirebase()` 交回 `resumeIntent` → **自動**開啟範本庫共享區並彈出**發布確認對話框**」，不是再跳登入提示。
- 檔案:行號：
  - `js/ui/sharearea.js:166`：`onResume(intent => { openSharedTab(); startPublish(intent); });`
  - `js/ui/sharearea.js:152-161`：`startPublish` 一看 `currentUser()` 是 falsy 就呼叫 `hooks.promptLogin(source)`，重新跳登入提示 modal，而不是直接開發布確認框。
  - 根因在 `js/store/firebase.js:58-64`：`load()` 裡，`await getRedirectResult(...)` 成功後**先**（第 61 行）`emit(resumeCbs, intent)` 同步通知所有 `onResume` 訂閱者，**之後才**（第 63 行）呼叫 `fb.au.onAuthStateChanged(fb.auth, u => { user = toUser(u); ... })` 去設定模組內的 `user` 變數。`onAuthStateChanged` 的初次回呼本身是非同步觸發（專案自己的測試假 SDK 在 `tests/unit/firebase.test.js:19` 用 `setTimeout(() => cb(authUser), 0)` 模擬這個非同步性），所以 `emit(resumeCbs, intent)` 執行的那一刻，`user` 一定還是 `null`／`userKnown` 還是 `false`。
- 重現方式：用專案現有的 `js/store/firebase.js`（原封不動）＋`tests/unit/firebase.test.js` 同款的 `fakeSdk`／`_resetForTest` 工具，模擬「`signIn()` 因 popup 被擋走 redirect → 下次載入時 `getRedirectResult` 回傳已登入的使用者」，並像 `sharearea.js` 一樣在 `onResume` 回呼裡呼叫 `currentUser()`：
  ```js
  // 用 tests/unit/firebase.test.js 的 fakeSdk/_resetForTest 手法
  const store = memStorage();
  store.setItem(RESUME_KEY, JSON.stringify({ action: 'publish', tplId: 't1' }));
  const back = fakeSdk({ redirectUser: { uid: 'u1' }, authUser: { uid: 'u1', displayName: 'Jay' } });
  _resetForTest({ config: CONFIG, load: back.load, storage: () => store });
  onResume(intent => console.log('currentUser() =', currentUser())); // 印出 null
  await initFirebase();
  ```
  實際跑出：`onResume` 觸發時 `currentUser() === null`；對應到 `sharearea.js` 的程式碼路徑，就是 `startPublish(intent)` 判斷「未登入」而呼叫 `hooks.promptLogin`，使用者會看到剛轉址登入回來卻又跳出一次「發布需要 Google 登入」的提示，而不是任務要求的「自動彈出發布確認對話框」。對使用者而言等於要多按一次登入（且會再開一次 `signInWithPopup`），不符合 AC-20 與 AC-21（「最多 2 次點擊」）的精神。
- 建議修法（擇一）：
  1. 在 `js/store/firebase.js` 的 `load()` 裡，把 `emit(resumeCbs, intent)` 移到 `onAuthStateChanged` 的**初次回呼**裡面觸發（即在 `user = toUser(u); userKnown = true;` 之後才 `emit`），確保 `onResume` 的訂閱者看到 `currentUser()` 時一定已經是最新登入狀態；或
  2. 讓 `resumeCbs` 傳出的值順便帶上使用者（例如 `emit(resumeCbs, { intent, user: toUser(r.user) })`），`sharearea.js` 的 `startPublish`／`onResume` 改用這個附帶的 user，不要依賴當下的 `currentUser()`。
- 這個問題正好落在任務檔「已知限制」自承沒有實機測過的那段（redirect 路徑），本次複審用程式碼時序分析＋腳本重現補上了驗證。
