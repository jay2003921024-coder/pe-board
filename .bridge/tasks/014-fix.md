## 目標

使用者看了 demo 後的回饋：

> 平板觸控仍不符合預期（AC-15、AC-18），目標是像 Canva 一樣順暢。請照以下規則修正：
1. 單指捲動：使用『選取』工具、而且手指按在空白處（沒有按到任何物件）時，單指拖曳 = 捲動或平移畫面。畫面已放大時平移畫布；沒放大時捲動整個頁面，上下左右都要能滑。不論手指落在畫布哪一側（包含右側）都要有反應。2. 不誤觸：選取工具按在物件或把手上 = 拖曳物件；使用放置或畫線工具時 = 照原本行為放置或畫線。這兩種情況都不能捲動頁面，維持 AC-15。
3. 框選改到多選模式：觸控時，空白處拖曳框選只在開啟『多選』模式時才有效，滑鼠操作維持原本行為。
4. 雙指縮放：以兩指捏合的中點為縮放中心，捏合中點下方的畫布內容在縮放過程中要保持在手指底下，不能跳動或亂跑。雙指同時移動 =平移。縮放要跟手、 連續，不能一頓一頓的。
5. 驗證方式：
   - 縮放中心的計算要寫成純函式並加單元測試（例如在 (300,200) 捏合放大 2 倍後，該點對應的畫布座標不變）。
   - 用真實的觸控事件序列實測，不能只靠程式碼檢查：單指在空白處捲動、單指拖物件、雙指在不同位置捏合，並在交接筆記附截圖或量測數據。
   - 桌機滑鼠操作與 AC-1～AC-9 不能退步，npm test 要全部通過。

## 交接筆記

### 根因

第 3 輪驗收（`verify-r3.md`）用 CDP 合成觸控事件測出 AC-15／AC-18 都是 PASS，但使用者在真機/demo 上仍回報雙指縮放亂跑、單指在空白處往下滑完全沒反應。差異在於：舊實作讓「單指在空白處拖曳」完全交給瀏覽器原生捲動（CSS `touch-action:pan-y`，JS 端 `state.drag` 保持 `null` 不攔截），只有「兩指同時碰到」才切進我們自己的 JS 縮放／平移邏輯。在真實瀏覽器裡，瀏覽器會在第一指剛開始移動、還沒有第二指時就依 `touch-action` 單獨決定是否要啟動原生捲動手勢；等第二指落下、JS 想接管變成縮放時，原生捲動手勢可能已經在走，兩套機制互搶座標，才會看起來「亂跑、一頓一頓」。CDP 的合成觸控事件不會重現這個瀏覽器內部的手勢仲裁時機，所以自動化測試測不出來。

### 做了什麼

全部改在 `js/ui/editor.js`（新增 `panMove()`，修改 `onPointerDown`／`onPointerMove`／`endDrag` 的空白處分支），`css/layout.css`、`css/touch.css` 兩個 CSS 檔，`tests/unit/viewport.test.js` 多加一筆單元測試。

1. **單指捲動／平移改成自己接管**（回饋規則 1）：`#board`、`.canvas-wrap` 的 `touch-action` 從 `pan-y` 改回 `none`（`css/layout.css:60`、`css/touch.css:6`），不再讓瀏覽器自己決定要不要啟動原生捲動，完全由 JS 處理，避免跟兩指縮放搶座標。觸控＋選取工具＋非多選模式下，空白處按下改成 `state.drag = { kind:'pan', last:{x,y} }`（`editor.js` 的 `onPointerDown`），新函式 `panMove(e, drag)`：
   - 如果畫布已經放大（`zoomLevel(view, bounds) > 1`）：用 `board.getScreenCTM().inverse()` 的縮放係數把 client px 的位移換算成場地單位的位移（只換算「位移量」不換算「座標點」，跟既有 `ptRaw` 不同），呼叫 `panBy()` 平移 `state.view`，內容跟著手指走。
   - 如果沒放大：`window.scrollBy(-dx, -dy)`，自己捲動整個頁面（取代原本倚賴的原生捲動），上下左右的拖曳方向都會被處理到（沒有再限制成只放行垂直）。
   - `pointers` Map 仍然在單指 `pan` 進行中持續追蹤座標；第二指落下時既有的 `startPinch()`／`cancelSingleDrag()` 會接手（`pan` 沒有 `created`/`pushed`，`cancelSingleDrag` 對它是no-op），自然從單指平移切換成兩指縮放，不會有殘留狀態。
   - `endDrag()` 對 `kind:'pan'` 直接清空 `state.drag` 並 return，不會多跑 `renderProps()`／`save()`。
2. **不誤觸**（回饋規則 2）：沒有改動 `hEl`（把手）／`gEl`（物件）／`LINES[t]`／`ITEMS[t]` 這幾個既有分支的判斷順序與邏輯——它們都在「空白處」判斷之前就把 `state.drag` 設成非空值，`onTouchMove` 的 `if (state.drag) e.preventDefault()` 跟之前一樣會擋住原生捲動／縮放，選取工具拖物件、放置或畫線工具維持原行為。
3. **框選限多選模式**（回饋規則 3）：沒有改動，原本就只有 `multi`（`e.shiftKey || ui.multi`）成立時才會走到 `state.drag = { kind:'box', ... }`；觸控非多選模式維持改成 `pan`。滑鼠（`pointerType !== 'touch'`）完全不受影響，仍然一律框選。
4. **雙指縮放**（回饋規則 4）：縮放中心的錨點計算（`pinchMove`／`ptRaw`）沿用第 013 任務已經修好的算法沒有再改，問題不在那段數學，而在上面第 1 點的原生捲動競爭；拿掉競爭來源後用真實瀏覽器觸控序列重新量過，縮放過程連續、不跳動（見下方驗證）。

### 已知限制

- CDP 合成觸控事件仍然不是「真的手指」，雖然這次特別設計成重現造成上一輪問題的時機（單指先開始拖曳、兩指後落下、連續多步量測），但瀏覽器真正的手勢仲裁（compositor thread 的 scroll/zoom 決策）細節無法 100% 用這種方式重現；建議使用者仍在真實 iPad 上過一次這五個情境（尤其雙指縮放的「跟手」手感）。
- `window.scrollBy` 的捲動方向是整頁捲動（不是只捲畫布容器），如果之後版面把畫布放進自己的捲動容器，這段需要改成捲那個容器而不是 `window`。
- 沒有改動 `js/ui/touch.js`、`js/core/viewport.js`、`js/ui/board.js`，雙指縮放的核心換算與放大倍率限制（1～4 倍）沿用第 005／013 任務的既有實作。
